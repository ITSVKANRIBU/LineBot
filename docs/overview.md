# システム概要

## 目的

対面で遊ぶ会話ゲーム「インサイダーゲーム」および「Werewords」で、**参加者それぞれに異なる秘密情報（役職とお題）を配る**ための Bot です。

これらのゲームは、進行そのものは人間が対面で行います。機械が必要なのは配役の瞬間だけです。紙やジェスチャーで役職を配ると、配る人が全員の役職を知ってしまう、配り間違える、参加者が自分の役職を確認し直せない、といった問題が起きます。LINE の 1 対 1 トークを配布経路にすると、各参加者は自分の情報だけを、いつでも自分の端末で確認できます。

Bot が担うのはこの一点です。ゲームの進行、勝敗判定、時間管理、得点集計は対象外です。

## スコープ

**扱うこと**

- 秘密情報の生成（役職の抽選、お題の抽選）
- 秘密情報の配布（参加者ごとに異なるメッセージを、参加順に配る）
- 配布状況の可視化（何人に配ったか、自分は何番目か）
- 任意のメッセージ集合の配布（特殊村。ゲーム種別を問わない汎用の配布機能）

**扱わないこと**

- ゲームの進行と勝敗判定
- ゲーム状態の永続化と履歴
- 利用者アカウント、認証、課金
- 複数プロセスでの状態共有

## 登場人物

| 呼称 | 説明 |
| --- | --- |
| オーナー | 村を作成した人。人数とお題を決め、参加者へ村番号を伝える |
| 参加者 | 村番号を送って役職を受け取る人 |
| GM | 進行役。お題を知るが推理には参加しない。神モードでのみ登場する |
| 村 | 1 回のゲームに対応する配布の単位。番号で識別する |
| お題 | 参加者が当てる対象の言葉 |

「村」は人狼系ゲームの慣用に倣った呼称で、1 ゲーム分の配布セッションを指します。

## 中心となる概念：村番号

利用者が Bot へ入力できるのは、LINE のトークに打てるテキストだけです。そのため、**村の識別子と操作の指示を、同じテキスト入力欄で表現する**必要があります。

このシステムは、数字の桁数で村の種別を分けることでこれを解決しています。

- 4 桁（1000〜9999）: 通常村・ランダム村
- 5 桁（10000〜99998）: 特殊村・Werewords 村

参加者に必要な操作は「数字を送る」だけになり、どのゲームで遊んでいるかを Bot へ伝える必要がありません。オーナーが村番号を口頭で伝えれば、参加者はその数字を送るだけで自分の役職を受け取れます。

この設計の代償として、数字の解釈がモードによって変わります。小さい数字は人数設定、大きい数字は村への参加として扱われます。境界の具体値と、そこから生じる制約は [game-spec.md](game-spec.md) と [interfaces.md](interfaces.md) に記述します。

## 設計原則

**1. 状態を持たない方向へ倒す**

ゲームは数十分で終わり、終われば状態に価値がなくなります。永続化すれば、スキーマ、バックアップ、マイグレーション、個人情報の保持期間という運用が発生します。このシステムはそれを引き受けず、**状態をプロセスメモリだけで保持し、再起動で失われることを受け入れます**。

失われて困るのは「再起動の瞬間に進行中だった村」だけです。その場合、オーナーが村を作り直せば復帰できます。

**2. 配布の一貫性を、応答の見栄えより優先する**

同じ村の中で配役の規則が混ざると、ゲームが成立しません。インサイダーがいない村や、役職が重複した村が生まれた場合、参加者はそれに気付けません。そのため、**配役に関わる状態遷移は不可分に行い**、途中経過が他の参加者から観測されないようにします（[architecture.md](architecture.md) 参照）。

**3. 秘密情報をログに残さない**

Bot が扱うのは、LINE ユーザー ID とお題です。前者は個人の識別子、後者はゲームの答えそのものです。**受信イベントそのものをログへ出力せず**、記録するのはイベント種別と処理結果までとします。

**4. 経路が違っても、ゲームの規則は 1 つ**

LINE からの操作と HTTP API からの操作で、村の作られ方や配役の決まり方が違ってはいけません。両者は同じゲーム操作を呼び出し、**経路ごとの差分は入力の解釈だけ**に閉じ込めます。

**5. 現在の要件を満たす最小の構成を選ぶ**

想定利用者は数十人規模の知人グループです。この規模で成立する最小の構成を選び、来るかどうか分からない負荷や機能のための抽象化を先に作りません。
