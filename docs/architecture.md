# アーキテクチャ

コンポーネントの境界と責務、状態の持ち方、並行性の扱い、そしてそれらを選んだ理由を記述します。

## 層と依存の向き

```text
┌─────────────────────────────────────────────────────┐
│ 入力アダプタ                                        │
│   LINE webhook ハンドラ／村操作 API／特殊村作成 API  │
│   責務：入力の解釈と、応答メッセージへの変換だけ    │
└───────────────────────┬─────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────┐
│ ゲーム操作                                          │
│   村の作成・人数設定・お題設定・逆村化・参加        │
│   責務：ゲームの規則。経路を知らない                │
└───────────────────────┬─────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────┐
│ 状態                                                │
│   村（通常／特殊）とレジストリ                      │
│   責務：状態の保持と、状態遷移の不可分性            │
└─────────────────────────────────────────────────────┘

補助：お題辞書（起動時に読み込む）、役職画像カタログ（定期取得）
```

依存は上から下への一方向です。状態層はどの経路から呼ばれたかを知りません。

### 入力アダプタの責務を「解釈だけ」に閉じる理由

LINE 経由と HTTP API 経由で、村の作られ方や配役の決まり方が違ってはいけません。両方の経路にゲームの規則を書けば、片方だけを直したときに挙動が分岐します。分岐しても、配布結果を突き合わせる利用者がいないため**誰も気付けません**。

そのため、経路ごとに違ってよいのは次の 2 つだけに限定します。

- 入力をどう解釈するか（数値の境界値、対応するコマンド）
- 結果をどう返すか（LINE への返信か、JSON か）

実際に、両経路で異なるのは数値の境界値と対応コマンドだけです（[interfaces.md](interfaces.md) の「数値の解釈」参照）。

### 「対象の村がない」を通常の結果として扱う

ゲーム操作は、対象の村が見つからない場合を**エラーではなく通常の結果**として返します。村が消えている、まだ作っていない、条件を満たさない、はいずれも利用者の操作として起こりうることで、例外的な事象ではないためです。

呼び出し側が経路に応じた応答へ変換します。LINE では村の作成を促す既定の応答、`/callapi` では `村が作成されていません` のテキストです。

## モジュール構成

Gradle のマルチプロジェクトビルドで、Bot 本体と LINE Messaging API SDK から構成されます。

```text
Bot 本体（ゲームロジックと公開 API）
  └─ Spring Boot 連携（webhook の受け口と自動設定）
       ├─ API クライアント（返信・プロフィール取得・リッチメニュー）
       ├─ サーブレット（署名検証と webhook 本文の解析）
       └─ モデル（メッセージ・イベントのデータ型）
```

SDK 部分は LINE 公式 SDK（line-bot-sdk-java）由来です。**このリポジトリに同梱されており、依存として取得していません。** SDK 側にも手が入っているため、上流の更新を取り込む際は差分の確認が必要です。

## 状態モデル

すべての状態はプロセスメモリ上にあります。データベース、ファイル、外部ストアは使いません。

### 通常村

| 項目 | 説明 |
| --- | --- |
| 村番号 | 4 桁。レジストリが採番する |
| オーナー | 作成者のユーザー ID |
| お題 | 一度だけ設定できる |
| 参加人数 | 一度だけ設定できる。設定と同時に配役が抽選される |
| インサイダーの位置 | 参加順の何番目がインサイダーか |
| GM の位置 | 神モードとランダム村でのみ有効 |
| 逆村フラグ | 参加者が 0 人のときだけ立てられる |
| ランダム村フラグ | 作成時に決まる |
| 参加者 | 参加順のリスト。各要素が席順と役職を持つ |

### 特殊村

| 項目 | 説明 |
| --- | --- |
| 村番号 | 5 桁 |
| メッセージ列 | 作成時にランダムに並べ替え済み。配布順そのもの |
| 参加者列 | 参加順のリスト。i 番目の参加者に i 番目のメッセージが対応する |

特殊村は役職も抽選も持ちません。**参加順とメッセージ列の添字の対応だけ**が状態です。この単純さのおかげで、Werewords も外部フォームからの任意の配布も同じ仕組みに乗ります。

### レジストリ

通常村と特殊村を、それぞれプロセス内のリストで保持します。

| 項目 | 通常村 | 特殊村 |
| --- | --- | --- |
| 上限 | 50 件 | 30 件 |
| 番号の範囲 | 1000〜9999 | 10000〜99998 |
| 超過時 | 古い村から削除 | 古い村から削除 |

番号は空いているものからランダムに採番します。連番ではないため、隣の番号を推測して他人の村へ入ることはできません。ただしこれは総当たりを防ぐ強度を持たず、認証の代わりにはなりません。

## 並行性

webhook は複数スレッドで並行に処理されます。同じ村に対して、オーナーの設定操作と参加者の入室が同時に届きます。

### 不可分に扱う操作

次の操作は、途中経過が他のスレッドから観測されてはいけません。

| 操作 | 途中経過が見えると起きること |
| --- | --- |
| 人数確定と配役抽選 | 配役が決まる前に参加者が着席し、役職を受け取れない |
| ランダム村のオーナー着席 | 他の参加者に席を奪われ、オーナーが配役されない |
| お題の設定 | 二重設定。後から送った文字列で上書きされる |
| 逆村への切り替え | 切替の前後で配役規則が混在し、村の中で役職が矛盾する |
| 参加（席の確保と配役） | 定員超過、または同じ席が二重に配られる |
| 村番号の採番と登録 | 番号の重複 |

**これらの不整合は、参加者からは検知できません。**インサイダーが不在でも、役職が重複していても、各参加者は自分の役職しか見えないため、ゲームがおかしいと気付いたときには終わっています。そのため、**性能より一貫性を優先**し、村単位およびレジストリ単位でロックを取ります。

### 排他の粒度

- **村ごと**: 1 つの村への操作は直列化されます。村が違えば並行に処理されます。
- **レジストリごと**: 採番と登録、および検索は直列化されます。

想定利用者は数十人規模で、1 つの村を同時に触るのは高々その村の参加者です。この粒度で性能上の問題は起きません。より細かい排他は複雑さに見合いません。

## 設計判断

### 状態を永続化しない

**判断**: データベースを持たず、状態をプロセスメモリだけで保持する。

**理由**: ゲームは数十分で終わり、終われば状態に価値がありません。永続化すれば、スキーマ、マイグレーション、バックアップ、そしてお題とユーザー ID という個人情報の保持期間管理が発生します。得られるのは「再起動をまたいで進行中の村が残る」ことだけで、その頻度は再デプロイの頻度に等しく、かつ利用者は村を作り直せば復帰できます。

**受け入れた代償**: 再起動で進行中の村が消えます。水平スケールできません。

### 配役を「席の位置」で決める

**判断**: 参加者ごとに役職を抽選するのではなく、人数確定の時点で「インサイダーになる席番号」を抽選し、参加順にその席へ着かせる。

**理由**: 参加者ごとに抽選すると、「まだインサイダーが出ていないから、残り 1 人は必ずインサイダー」という補正が必要になり、途中で参加が止まった場合の扱いが破綻します。席で決めれば、**誰が何人参加しても配役の規則は変わりません**。

**受け入れた代償**: 定員に満たないままゲームを始めると、インサイダーが不在になり得ます。人数を守るのは利用者の責任です。

### 上限超過時に古い村を消す

**判断**: レジストリが上限に達したら、新しい村の作成を拒否せず、古い村を削除する。

**理由**: 上限がなければメモリが際限なく増えます。作成を拒否すると、**過去の誰かが放置した村のせいで、今から遊ぶ人が村を作れなくなります**。古い村は使われないという前提のもと、新しい村の作成を常に成功させる方を選んでいます。

**受け入れた代償**: 短時間に大量の村が作られると、進行中の村が消えます。公開 API が無認証であるため、これは意図的に引き起こすこともできます（後述）。

### 秘密情報をログに出さない

**判断**: 受信イベントそのものをログへ出力しない。記録するのはイベント種別と処理結果まで。

**理由**: webhook イベントには LINE ユーザー ID とお題が含まれます。前者は個人の識別子、後者はゲームの答えそのものです。デバッグのためにイベントをそのまま出力する実装は一般的ですが、**この Bot ではログがゲームのネタバレになります**。

同じ理由で、公開 API の予期しないエラーは定型のメッセージへ丸めます。フレームワークの既定のエラー応答は例外メッセージとリクエストパスを含み、そこにお題やユーザー ID が現れ得るためです。丸め方は API ごとに異なり、`/callapi` は HTTP 500 の定型 JSON、`/specialvillage` は本文なしの HTTP 400 です（[interfaces.md](interfaces.md) 参照）。

**受け入れた代償**: 障害調査でイベントの内容を追えません。イベント種別だけはログレベルを上げて確認できます（[operations.md](operations.md) 参照）。

### 役職画像のカタログを外部化する

**判断**: 役職に添える画像の一覧を、外部のウェブアプリから定期取得する。

**理由**: 画像を差し替えるたびに再デプロイするのを避けるためです。画像は見た目の要素であり、アプリケーションのリリースサイクルに縛る理由がありません。取得に失敗しても前回の一覧（一度も取得できていなければ既定画像）で配布を続行するため、外部依存が可用性を下げません。

### ランダム村を隠しコマンドにする

**判断**: `ランダム` を実装しつつ、既定の応答が案内する選択肢には含めない。

**理由**: 既定の応答は「Bot の使い方が分からない人」に向けたものです。選択肢を増やすほど、最初の一歩が分かりにくくなります。ランダム村は慣れた利用者向けの短縮経路であり、案内すべき入口ではありません。

## 既知の制約

いずれも意図的に、または現時点の判断として受け入れているものです。解決すべき課題と認識しているものは [roadmap.md](roadmap.md) を参照してください。

### 単一プロセス前提

状態がプロセスメモリにあるため、複数インスタンスで動かすと村が共有されず、参加者が「村が作成されていません」を受け取ります。**スケールアウトはできません。**

### webhook の応答時間

LINE プラットフォームは webhook に 2 秒以内の応答を求めます。現在の実装は返信 API の応答を同期的に待ってから webhook へ応答します。返信 API が遅延すると 2 秒を超え得ます。

現に稼働しているため実害は出ていませんが、**設計上の時限爆弾**として認識しています。解消には返信の非同期化が必要で、これはアプリケーションの返信アーキテクチャの変更にあたります。

### 公開 API が無認証

`/callapi` と `/specialvillage` は認証もレート制限も持ちません。次のことが可能です。

- **他人としての操作**: `/callapi` の `userId` は呼び出し元が指定します。他人の LINE ユーザー ID を知っていれば、その人の村を操作できます。
- **進行中の村の追い出し**: 無認証のリクエストを 50 回（特殊村なら 30 回）送るだけで、進行中の村をすべてレジストリから追い出せます。

これらは、外部フォームからブラウザ経由で村を操作するという要件と、LINE ユーザー ID 以外の識別子を持たないという前提から生じています。解消には認証の導入が必要で、外部フォーム側の改修を伴います。

### 経路ごとの数値境界の不一致

LINE 経由と `/callapi` 経由で、数値の解釈の境界が異なります（[interfaces.md](interfaces.md) 参照）。統一するとどちらかの経路の既存利用者に影響が出るため、既知の差分として記録しています。

### お題辞書が行番号に依存する

難易度が辞書の行番号の範囲として表現されているため、辞書の行を追加・削除・並べ替えると難易度の境界がずれます。辞書を更新する場合は境界値も併せて見直す必要があります。
