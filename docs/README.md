# 設計ドキュメント

インサイダーゲーム Bot の設計ドキュメントです。外部から観測できる仕様と、設計上の判断とその根拠を記述します。実装の詳細（クラス構成、メソッド、ファイル配置）はコードを参照してください。

## 読み分け

| 文書 | 内容 | 主な読者 |
| --- | --- | --- |
| [overview.md](overview.md) | システムの目的、スコープ、登場人物、設計原則 | 全員。最初に読む |
| [game-spec.md](game-spec.md) | ゲームの外部仕様。村の種類、コマンド、役職決定規則 | 仕様を確認する人、Bot を使う人 |
| [interfaces.md](interfaces.md) | 外部インターフェースの契約。webhook、公開 HTTP API、外部依存 | 連携するクライアントを書く人 |
| [architecture.md](architecture.md) | コンポーネント境界、状態モデル、並行性、設計判断の根拠 | 変更を加える人 |
| [operations.md](operations.md) | 実行環境、設定、デプロイ、ログ方針、障害時の挙動 | 運用する人 |
| [roadmap.md](roadmap.md) | 今後の計画。現時点で検討中のもの | 全員 |

`superpowers/specs/` には、個別の変更に対する設計スペックを日付付きで置きます。上記の文書がシステムの現状を表すのに対し、スペックは特定の変更の提案とその検討過程を残すものです。両者が食い違う場合、現状を表すのは上記の文書です。

## 記述の方針

- 外から観測できる振る舞い（入力に対する応答、エラー時の応答、上限と超過時の挙動）を書く。
- 設計判断は、何を選んだかではなく、なぜそれを選び、何を受け入れたかを書く。
- コードを読めば分かることは書かない。二重管理になり、片方が必ず古くなるため。
- 未対応であることが意図的な選択なら、その旨を明記する。
